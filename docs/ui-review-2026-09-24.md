## 开工前先记住：现在做对了什么

1. **外壳的纵向成本真的降下来了。** 品牌、主导航、两个驻留标签合成一条左侧栏，`.app-rail { position: sticky; top: 0; height: 100vh }`（`src/styles/shell.css`）让内容列从窗口顶部开始，不再是旧注释里那 149px 的双横条。
2. **折叠控件的可达性做对了。** `aria-expanded` + `aria-controls="app-primary-nav"`、用动作词做 title/aria-label，且 `railIsCollapsed()` 优先报告 CSS 实际会给的形态，所以在 1175px 下它显示的是「展开」而不是一个点了没反应的「收起」（`src/app/AppShell.tsx:233-247`、`src/lib/rail.ts:100-118`）；860px 以下直接 `display: none`，不留失效按钮（`shell.css:351-355`）。
3. **空状态分得清，也给了下一步。** 世界库把「搜索无结果」与「档案中还没有世界」分成两句不同的标题，各自给出「清除搜索」/「去『导入与设置』添加根目录」（`src/components/WorldLibrary.tsx:287-295`）；时间线同样（`src/components/Timeline.tsx:213-218`）。
   _修正一条上一轮的说法_：hero 尺子对缺失世界写「已缺失」，**但下方列表对同一个世界写 `0s`**——本轮在数据态截图里目视到（`Dashboard.tsx:106-112` 无 missing 判断，`:209-213` 有）。所以「缺失不显示 0 秒」只对尺子成立，这本身已升格为一条严重问题（S5b）。
4. **数字与刻度的底层逻辑是干净的。** 所有数值统一 `var(--font-mono)` + `font-variant-numeric: tabular-nums`；排行与尺子的比例只在 `src/lib/dashboard.ts:45-60` 定义一次（`rankingMax`/`rowShare`），两个界面共用同一个计算，`max <= 0n` 时不画条。

## 一、为什么现在的界面显得混乱又丑

### 1. 没有「全局尺度」，而且**门禁把现状当成了标准**

字号 7 级（`tokens.css:20-26`），正文 13px，用得最多的两档是 12px（95 处）与 11px（32 处）。更关键的是：**仓库自己的设计门禁 `scripts/qa-design-check.mjs` 把 `TYPE_SCALE = [11,12,13,15,18,22,28]`、`TYPE_FLOOR = 11` 写死在 `:33-35`**。我本轮跑它，14 组页面 × 主题全部 PASS。也就是说：**门禁全绿不代表尺度对，它只是在维护“当前的尺度”**——这正是「改了好几版还是丑」的机器原因：每版都能通过检查，而检查本身站在错误的一边。

> 反证来自平台方：微软 Windows 排版规范写明「Minimum values: 14px Semibold, 12px Regular — Text smaller than these sizes and weights are illegible in some languages」，即 **12px 常规体是下限、14px 才是正文**。我们的 11px（32 处）在这条线以下，13px 正文也低于正文标准。
> **代价**：用户得到的是「字小、灰、糊」，说不出哪里乱但读起来累；而每次改版都合规，所以没人能靠检查发现问题。

### 2. 同一个信息被表达两次，而且**两次互相打架**

概览页 hero 的尺子与下方排行列表读同一个数组（`Dashboard.tsx:321` 与 `:406`），字号不同（实测 `.ruler-name` 12px vs `.ranking li` 13px）；**同一个缺失世界，尺子写「已缺失」、列表写 `0s`**（本轮数据态实测）。此外 `RankingChart.tsx` + `echarts` 依赖 + 3 条 CSS 是完整死代码，顶部状态条与页尾「连接状态」各说一套。

> **代价**：用户看到同一行两个不同答案，第一反应是「数据不可信」——这是数据类工具最贵的一种损失。

### 3. 外壳只解决了「少占地方」，没解决「一眼看得懂」

七个同级入口平铺无分组；≤1400px 时标签全部隐藏（本轮实测 1175px：7 个 `.app-nav-label` 全 `display:none`、rail 72px、内容列 1031px）。

> **但本轮也测出了更好的消息**：强行在 1175px 打开标签后，192px 侧栏**没有任何溢出**（按钮宽 179px、label 39–65px、文档横向溢出 0、正文列 911px）。**所以 1400px 这个阈值不是「装不下」，而是一个产品取舍**（源码注释 `shell.css:239-252` 自己写了原因：它原本是为了保护设置页的两列布局，而那个布局现在只有 ≥1600px 才存在）。
> **代价**：约 1175px 的窗口里导航是一列没有字的 15px 图标，只能悬停试。

### 4. 状态语义不可信，用户学会了不看它

数据没回来先写「追踪已暂停」（`trackingStatus` 初值 `null`）；四个状态类只有三套样式；运行/暂停共用同一个绿点；深色下四种状态被一条特异性更高的规则压成同一个底色（实测：`.status-center.is-paused` 背景 `rgb(24,35,30)`、点色 `rgb(52,211,153)`）。

> **代价**：这条状态条不是信息而是噪音；它最该起作用的时刻（首帧、失败）恰恰给出错误结论。

### 5. 留白与层级不成立，靠容器代替分组

设置卡片内 18px、卡片间 16px（差 2px）；统计表里 15px 的字段名比它自己的 13px 读数更重（本轮实测 `statLabelFs=15px`、`tableFs=13px`、`valueAlign=start`、`thSticky=static`）。

> **代价**：找不到重点，看到的是「挤」，而不是「有秩序」；100 行的表滚下去就忘了列头。

## 二、界面不足清单

> 排序按「是否影响看懂 / 信得过」。新增项 **S5b、S7b** 是本轮实测发现的，前一轮的 **S5 距离断言已修正**。

### 严重

**S1 · 侧栏在 1400px 以下只剩图标** — `src/styles/shell.css:316`（另见 `AppShell.tsx:211-215`）

- 问题：默认偏好是 `auto`（不写 `data-rail`），≤1400px 时 `:root:not([data-rail='expanded']) .app-nav-label/.wordmark-label/.local-label { display: none }`，侧栏切到 `--sidebar-w-compact: 72px`（`tokens.css:67`）。
- 代价：导航变成一列无字图标，用户要悬停七次才知道通向哪里。
- 证据：`shell.css:239-240` 注释自述「The user's window is ~1175px」；`AppShell.tsx:211/215` 的 `title` 与 15px 图标是仅剩表达手段。
- 对照原则：侧栏管去向（导航必须一眼可读）；Fluent 2 Nav 官方页本轮已核验：「By default, Nav is set to 260 pixels wide. At 640 pixels screen width, it becomes an overlay drawer.」
- 标记：**【本轮实测】** 1175px 下 7 个 label 全部 `display:none`、rail 72px、列宽 `72px 1031px`；1440px 下全部 `display:block`、rail 192px。

**S2 · 字号阶梯 7 级、正文 13px，且门禁把 11px 当合法下限** — `tokens.css:20-26`、`scripts/qa-design-check.mjs:33-35`

- 问题：11/12/13/15/18/22/28 七级；`:root`、`body` 都钉 13px（`styles.css:12`、`:38`），`small` 钉 11px（`:25-27`）。计数：caption 95、micro 32、body 32、lead 18、title 9、heading 3、display 3——用得最多的两档都低于正文。
- 代价：整屏小字是「丑」最真实的来源；而门禁认定「11px 合法、13px 是正文」，所以任何一次改版都不会被拦。
- 证据：`grep -ro -- "--type-micro" src | wc -l` = **32 处**（含 `tokens.css` 里 1 处定义 → 实际使用 **31 处**：`styles.css` 22、`warmth.css` 2、`pages.css` 7）；上一轮报告里 31 与 32 的差异即此（前一轮写「全仓 31 处」指使用、写「micro 32」指含定义，本版已统一口径）。
- 对照原则：Windows 排版规范（本轮已核验）：Caption 12/16、Body 14/20、Subtitle 20/28、Title 28/36，并明确「12px 是常规体下限、14px 正文」；Atlassian 排版（本轮已核验）：body 14/20、body.small 12/16、metric 16/20 与 28/32。
- 标记：**【本轮实测】**（计数 + 门禁运行）。

**S3 · 状态条把「未知」写成「已暂停」，绿点兼表运行与暂停** — `AppShell.tsx:36`（另见 `pages.css:191-216`、`warmth.css:736-739`、`styles.css:1052-1061`）

- 问题：标签链末端 `'追踪已暂停'`，而 `trackingStatus` 初值 `null`；tone 有 `is-error/is-running/is-ready/is-paused` 四类，CSS 只有三套（`.is-ready` 全仓只出现在 `AppShell.tsx:34`）；`.watch-dot` 与 `.watch-dot.active` 同为 `var(--surface-strong)`；深色下 `:root[data-theme='dark'] .status-center`（(0,3,0)）压过 `.status-center.is-running`（(0,2,0)）。
- 代价：状态条在最需要它的时候给出错误结论。
- 对照原则：显式空态必须区分加载中 / 未配置 / 无结果；状态色要真的区分状态。
- 标记：**【本轮实测】** 深色 1366px：`.status-center.is-paused` 背景 `rgb(24,35,30)`、`.watch-dot` `rgb(52,211,153)`（亮绿）。**【上游复核】** 四类三样式。

**S4 · 七个同级入口平铺，配置页与业务页平级** — `src/app/routes.ts:12`（另见 `AppShell.tsx:201-222`）

- 问题：`PAGE_IDS` 七个 id 直接 `map` 成七个 `<button>`，无标题、分隔或子容器。
- 代价：侧栏不表达用途，每次都要重读七个标签；新增页面只会让这一列更长。
- 对照原则：侧栏分组导航；Fluent 2 Nav 本轮已核验「Nav only supports one level of nesting」「up to two levels of hierarchy」。
- 标记：**【上游复核】**。

**S5 · 概览页把同一份排行画了两遍（距离断言已修正）** — `Dashboard.tsx:174`（另见 `:47`、`:321`、`:383-393`、`:406`）

- 问题：hero 尺子与下方列表读同一个 `panel.rows`；行名字号 12px vs 13px（实测）；`slice(0, 7)` 与 `useState(5)` 两个不同的上限。
- **修正**：上一轮写「切换控件位于 hero 下方约 300px 处」——**本轮数据态实测不成立**：`.ranking-switch` top=455，尺子 bottom=422（只差 33px），列表 top=515。真正的问题是它改变了**位于它上方**的尺子，而用户在看下面的列表。另外「7 行 vs 5 行」只在世界数 >7 时才会分叉（fixture 只有 3 个世界，两处都是 3 行）。
- 代价：同一屏两组「排行」，参数不同、格式不同，用户不知道信哪个。
- 对照原则：一屏一个问题；参考 VS Code「已有功能不在别处再放一遍」【未核验转述】。
- 标记：**【本轮实测】**（行数、字号、几何全部实测；距离断言修正）。

**S5b · 同一个缺失世界，尺子写「已缺失」、列表写 `0s`**（本轮新增） — `Dashboard.tsx:106-112` 对 `:209-213`

- 问题：列表的 `.rank-duration` 直接 `formatCompactTicks(r.ticks.toString())`，没有 `row.missing` 判断；尺子有（注释还专门解释了为什么不能写 0 秒）。
- 代价：同一屏同一个世界的两个读数互相矛盾，直接击穿数据可信度；而且列表那个 `0s` 会被读成「从来没玩过」。
- 证据：`dashboard-1175-data.png` 中 `03 Removed World（已缺失）` 行尾为 `0s`，而尺子同一行写「已缺失」。
- 对照原则：同一量全站一种表达；空数据不渲染成 0。
- 标记：**【本轮实测】**。

**S6 · 「未选择玩家」被表达成「没有数据」** — `src/lib/dashboard.ts:132`（另见 `Dashboard.tsx:137/169/306`）

- 问题：`uuid === null` 时每个世界都被 `continue`，`current` 保持 `0n` → hero 渲染 `0s`；尺子因 `max <= 0n` 整块不渲染；列表给「还没有可排行的历史读数」；该状态持久化，下次启动照样看到空仪表盘。
- 代价：**【推断】**用户会以为数据丢了，跑去重新扫描/重新导入（本轮未做用户测试，这是基于因果链的推断，不是观测结果）。
- 对照原则：可行动空状态；空数据不渲染成 0。
- 标记：**【上游复核】**；我本轮另跑 `npx vitest run src/lib/duration.test.ts` → 31 passed（含 `['0','0s']`）。

**S7 · 统计页在表格之前连排 9 段控制/信息带** — `Statistics.tsx:277`

- 问题：渲染顺序为 heading(260) → ActivityFilters(269) → **图标工具栏(277)** → 口径 tabs(306) → ReadStatus(403) → filter-summary(404) → 统计概览(437) → 类别 tabs(480) → 搜索(542) → 表格(568)。
- 代价：一屏 2/3 是控件，用户要滚过一整屏才看到数据。
- 对照原则：一屏一个问题；两层披露；Power BI（一屏不放滚动条、最高层级放左上）【未核验转述】。
- 标记：**【本轮实测】** 数据态 y 坐标：图标工具栏 229、概览 417、类别 476、搜索 516、表格 **568**（视口 900）。

**S7b · 统计页首屏没有任何排序/冻结能力，且表头比正文还小**（本轮新增细节） — `styles.css:1936-1945`

- 问题：`.statistics-table table { font-size: var(--type-body) }` = 13px，而 `.statistics-table th { font-size: var(--type-caption) }` = 12px、`text-align: left`；`.statistics .statistics-table th`(2329-2334) 有 `background` 却 `position: static`。
- 代价：列头比数据小、又会在滚动时消失——100 行的表滚到中段就不知道每列是什么。
- 标记：**【本轮实测】** `thFs=12px`、`tableFs=13px`、`thSticky=static`、`valueAlign=start`。

**S8 · 统计表里字段名比读数更重，数值不右对齐** — `styles.css:2349-2355`

- 问题：`.stat-label` 15px/650 vs 表格 13px；`.stat-value`（`pages.css:401-404`）只有 mono 与 tabular-nums，无字号、字重、对齐。
- 代价：纵向没法比数——这正是统计页存在的理由。
- 对照原则：Atlassian `font.metric` 分级（本轮已核验 metric.small 16/20、medium 24/28、large 28/32，均加粗）；表格数字右对齐、冻结表头。
- 标记：**【本轮实测】**。

**S9 · 实例页紧跟实例名的时长是「游戏根目录合计」而非实例时长** — `PclInstances.tsx:180-189`（配合 `:77-81`、`:99-104`）

- 问题：渲染的是 `ticksForRoot(instance.game_root)`，与分组标题（`:162-167`）那个去重后的根目录总量同源。**后端没有实例级时长**：`src-tauri/src/database/read_models.rs:34-46` 的 `ScanSummary` 只有 `instances` 与 `roots`，`RootSummary` 只到世界；`src-tauri/src/launcher/mod.rs` 的 `DiscoveredInstance` 只有 `game_root`；`src-tauri/src/database/tracking.rs:110-118` 的 `InstancePseudo` 也是按 `game_root` 归口的秒数。
- 代价：用户据此判断「哪个实例玩得久」会得出错误结论；同数字在一行里出现两次像算错。
- 对照原则：主指标与标签必须同口径；汇总只应出现一次。
- 标记：**【本轮实测】** 数据态两者都是 `1449h 40m 43s`（同一数字）；**【上游复核】** 口径定义。

**S10 · 设置页两种宽度制度（结论已按实测修正）** — `ArchivePages.tsx:191` 与 `:271-289`（另见 `styles.css:73-82`）

### 治理机制（防止再回退）

- **单一来源**：字号、间距、颜色只在 `tokens.css` / `warmth.css` 定义；组件样式表禁止字面色值与字面 px 间距（由第 4 条断言守）。

- **门禁即契约**：`scripts/qa-design-check.mjs` 的 `TYPE_SCALE` 从「现状快照」升级为「设计契约」，改它必须与改 `tokens.css` 同一个提交。

### 要不要引入现成设计系统？（简短取舍）

**建议不引入组件库，只采纳外部尺度。** 理由：① 应用只有 7 个页面，且已有自己的原语（`ui/index.tsx`）、门禁与 86 个 QA 脚本，引入 Radix/shadcn 之类会把「手写 CSS」的既有资产变成混合体；② 真正缺的不是组件，而是尺度与约束，而尺度可以直接抄——本报告 B1 就直接采用了 Windows ramp（12/14/20/28，本轮已核验）与 Atlassian 的 metric 档（16/20/24/28，本轮已核验）；③ 若要借鉴组件行为（tabs、nav），优先照 Fluent 2 的规则补自己的原语。**唯一例外**：如果后面要做上拉菜单、可访问性要求更高的复合组件（combobox、日期选择），那时再评估引入无样式基座（Radix 之类），而不是现在就整体迁移。
